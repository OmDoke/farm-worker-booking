Introduction</h1><h2>1.1 Purpose</h2><p>This document describes the requirements for a web-based platform that allows farm owners (customers) to search for, book, and pay agricultural workers for farm tasks — primarily grape cultivation work such as pruning, thinning, bagging, spraying, harvesting, and packing. It is intended as a single reference for design, development, and testing so the whole project can be built from one source of truth.</p><h2>1.2 Project Overview</h2><p>The platform connects two sides of a local market: farm owners who need skilled labor for specific, time-bound farm tasks, and workers who offer those skills. Customers describe their farm (size in acres) and the work needed; the system matches and books an available worker for the requested date and location. Workers also have a direct, self-service way to join the platform (see Section 3.3 and Section 10). The homepage and core screens are shown in the customer's native language (e.g. Marathi), since the primary users are local farm owners and workers, not necessarily English-fluent.</p><h2>1.3 Scope</h2><p><strong>In scope for Version 1 (MVP):</strong></p><ul><li>Customer web app: browse/search workers, create a booking, choose a payment method, track booking status, rate the worker after the job.</li><li>Worker web app: self-register (create a profile via a dedicated sign-up entry point), list skills/services and service area, accept or decline bookings, mark job complete.</li><li>Admin panel: approve new worker profiles, manage service categories, view all bookings, handle disputes, view basic reports.</li><li>Mobile-responsive web application (works on phones and desktops) — no native app in V1.</li></ul><p><strong>Out of scope for Version 1:</strong></p><ul><li>Native iOS/Android apps (can reuse the same backend later).</li><li>Support for crops/tasks outside the initial process list (extensible later by admin).</li><li>Multi-country or multi-currency support.</li></ul><h2>1.4 Definitions and User Flow</h1><p>The platform uses a single, unified sign-up/login flow based on mobile number + OTP verification, rather than separate 'guest booking' and 'create account' paths. This avoids collecting the same details twice and confirms the customer's phone number is real and reachable, which matters because a worker will be sent to their location. Workers use the same OTP mechanism but land on a separate self-registration entry point described in Section 3.3.</p><h2>3.1 Customer booking flow</h2><table><thead><tr><th><p><strong>Step</strong></p></th><th><p><strong>Screen / Action</strong></p></th><th><p><strong>Details captured</strong></p></th></tr></thead><tbody><tr><td><p>1</p></td><td><p>Homepage</p></td><td><p>Farm/worker imagery and content shown in native language (e.g. Marathi); "Book Worker" button placed prominently.</p></td></tr><tr><td><p>2</p></td><td><p>Tap "Book Worker"</p></td><td><p>Starts the booking flow.</p></td></tr><tr><td><p>3</p></td><td><p>Mobile number + OTP</p></td><td><p>Mobile number entered, OTP sent and verified. System Architecture and API Design</h1><h2>10.1 Architecture layers</h2><p>The system is organized in four layers, kept intentionally simple so the whole MVP can run on free-tier infrastructure with one deployable unit:</p><ul><li>Presentation layer — Next.js pages for homepage, customer booking flow, worker self-registration and dashboard, and admin panel, rendered server-side for speed and search visibility.</li><li>Application/API layer — versioned Next.js API routes under /api/v1 handle authentication (OTP), worker registration, booking creation, matching logic, payment initiation, and payment webhooks.</li><li>Data layer — the database (MongoDB or PostgreSQL) stores users, worker profiles, bookings, payments, and reviews, as defined in Section 7.</li><li>Third-party services layer — SMS/OTP provider, payment gateway (with UPI QR generation), image storage, and maps/geocoding service, called from the API layer only, never directly from the browser except for signed, time-limited upload URLs.</li></ul><p>All customer and worker traffic flows through the same Next.js application; there is no separate backend service required for the MVP, which keeps hosting free and the codebase simple to maintain. If traffic outgrows a single Vercel deployment, the API routes can be lifted into a standalone Node service without changing the contract in Section 10.3.</p><h2>10.2 API design principles</h2><ul><li>REST-style, versioned routes under /api/v1/... so future breaking changes don't affect existing clients.</li><li>Stateless auth — after OTP verification, the client receives a short-lived JWT (access token) plus a longer-lived refresh token; every protected route validates the JWT and role claim (customer / worker / admin).</li><li>Consistent response envelope: { "success": boolean, "data": ..., "error": { "code", "message" } }, so the frontend has one error-handling path.</li><li>Rate limiting on POST /api/v1/auth/otp/request and /otp/verify (e.g. 5 requests/hour per mobile number) to stop OTP-bombing abuse — a common gap in first builds.</li><li>Idempotency on payment webhooks: the gateway's event ID is stored and re-deliveries are ignored, so a network retry can never double-mark a booking as paid.</li><li>File uploads (photo, ID proof) never pass through the API server as raw bytes — the API issues a short-lived signed Cloudinary upload URL and the browser uploads directly, then sends the resulting URL back.</li></ul><h2>10.3 Core API endpoints</h2><h3>Auth</h3><table><thead><tr><th><p><strong>Method</strong></p></th><th><p><strong>Path</strong></p></th><th><p><strong>Purpose</strong></p></th></tr></thead><tbody><tr><td><p>POST</p></td><td><p>/api/v1/auth/otp/request</p></td><td><p>Send an OTP to a mobile number (role: customer or worker).</p></td></tr><tr><td><p>POST</p></td><td><p>/api/v1/auth/otp/verify</p></td><td><p>Verify OTP;
